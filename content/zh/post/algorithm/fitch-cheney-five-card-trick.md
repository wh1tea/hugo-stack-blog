Fitch Cheney 的五牌魔术里，观众抽 5 张，助手摆出其中 4 张，魔术师凭这 4 张的顺序说出藏牌。规则本身不难：5 张牌必有 2 张同花色，这两张在 A→2→…→K→A 的循环里总有一个方向距离不超过 6 步；剩下 3 张的 6 种排列编码这个距离。

真正容易出错的是编码协议里的一个细节——**3 张牌怎么排序**。如果助手和魔术师两端的比较函数不一致，6 种排列的编号就全乱了[^1][^2]。

## 排列编码需要一副全序

编码依赖一个前提：给定 3 张牌，它们的「自然顺序」是唯一的。魔术师看到这 3 张，要能算出助手当初把哪张放第一位、哪张放第二位。

扑克牌只有两个属性：点数 `r`（A=1 … K=13）和花色 `s`。3 张牌点数撞车的概率不低，光靠点数排不出全序。所以协议必须约定：点数相同时怎么办。

## 排序键：先点数，后花色

实现里就一行：

```js
rest.sort((x, y) => (x.r - y.r) || (x.s - y.s));
```

`x.r - y.r` 先按点数升序；结果为 0 时 `||` 继续求值右边，按花色索引升序。花色索引来自数组下标：

```js
const SUIT_CHARS = ['♠', '♥', '♦', '♣'];   // s = 0, 1, 2, 3
```

于是点数相同时的大小约定是 `♠ < ♥ < ♦ < ♣`。

这里要强调：这个顺序**不是扑克里的花色大小**（桥牌里通常是 ♠ > ♥ > ♦ > ♣），而是纯粹为编码约定的。协议只要求两端一致，不要求它符合任何外部惯例。改成 `♣ < ♦ < ♥ < ♠` 也完全可以，只要编解码两侧同时改。

举个具体例子。剩下 3 张是「7♠、7♥、3♦」，排序结果是：

```text
3♦ < 7♠ < 7♥
```

于是 `7♠` 是 `rest[1]`，`7♥` 是 `rest[2]`，`3♦` 是 `rest[0]`。助手用一张 `PERMS` 表把 1–6 映射成 `rest` 的下标序列，魔术师反向查表，两边对「第 0/1/2 张是谁」的理解必须完全一致。

## 解码端复制同一个比较函数

解码侧的代码：

```js
const sorted = rest.slice().sort((x, y) => (x.r - y.r) || (x.s - y.s));
const idx = rest.map(c => sorted.indexOf(c));
```

`slice()` 先复制一份再排序，避免改动原数组。因为比较函数与编码端逐字相同，`sorted` 的顺序必然等于助手当时的排序，`indexOf` 才能把每个位置还原成 0、1、2。

## indexOf 靠的是对象引用

上面那行 `indexOf` 能工作，有个隐含条件：`rest` 和 `sorted` 里装的是同一批对象引用。`slice()` 是浅拷贝，元素还是原来那些 `{ r, s }` 对象，所以 `indexOf` 用引用相等就能命中。

一旦牌对象被复制过——从 `localStorage` 读回来、经过一次 `JSON.parse(JSON.stringify(...))`、或者为了「不修改原数组」而做了深拷贝——引用就断了，`indexOf` 全部返回 `-1`，解码静默出错。更稳的写法是按值比较：

```js
const idx = rest.map(c =>
  sorted.findIndex(o => o.r === c.r && o.s === c.s)
);
```

`(r, s)` 在整副牌里唯一，按值查找不会撞上两张牌。代价是 O(n²)，n=3 时可以忽略。

## 结语

这个细节的教训不是「花色顺序该怎样」，而是：**编码协议里的每一个约定都必须在两端同时成立**。排序键、平局规则、`PERMS` 表的下标起点，任何一处不一致，错误都会以「魔术师说错牌」的形式出现，而且很难从结果反推是哪一步出的问题。改协议时把编解码两侧的代码放在一起看，比单独测试每一侧有效得多。
